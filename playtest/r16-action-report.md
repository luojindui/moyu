## 1. 点击/连击

| 指标 | 实测 |
|---|---|
| JS handler 耗时 | **0.1ms**（0–0.2ms，n=4） |
| 点击→下一帧（上屏起点） | **13.7 / 13.7 / 14.2 / 15.2 ms**（60fps，≤1 帧） |
| 音效调度延迟 | **+0.0–0.2ms**（handler 内同步创建振荡器） |
| 飘字 | handler 内同步加入（冒泡监听里已可见），寿命 0.65s，最多 14 条 |
| HUD 连击数字 | 刷新滞后 **122–156ms**（150ms 节流）→ 数字比音效/飘字慢半拍 |
| 可点区域 | canvas 9 个位置全部计点击（无死区） |
| 连击窗口 | 间隔 0.30/0.45s → 5 击到 连×4；**间隔正好 0.50s → 连击完全不涨**（`gap<0.5` 边界）；0.55/0.70/1.05s → 不涨 |
| 封顶 | 第 21 击起每击收入恒 **1.24**（=×1.24 封顶精确）、HUD 显示 `连×20` |
| 音高映射 | 330→660Hz，21 级，实测序列与 `330·2^(min(combo,20)/20)` 逐点吻合；6/12/20 连加双音（406+609 / 500+750 / 660+990） |
| 断连音 | 停手 ~1.0s 后 110Hz 闷响 ✓，HUD 连击隐藏 |
| 80ms 防连点冷却 | 45ms 间隔狂点 24 次 → **只接受 12 次（50% 静默丢弃）**；约 >12.5cps 的连点有一半"点了没反应" |

结论：连击**跟手**（反馈同步、≤1 帧上屏、音高变化清楚），两个体验毛刺是 HUD 数字滞后 ~150ms 和 >12.5cps 静默丢弃。

## 2. 节奏点击（120BPM）——重点

### 2.1 判定窗口（逐 δ 实测，UI 判定文字/分数/节拍点颜色三方一致）

| δ（相对拍点） | 结果 |
|---|---|
| 0 / +0.05 / +0.075 / −0.075 / −0.079 | **PERFECT**（+20） |
| +0.081 / +0.085…+0.158 / −0.081 / −0.159 | **GOOD**（+10） |
| +0.159 / +0.161 / +0.165 / −0.161 … | **MISS** |
| 与规格 ±80ms/±160ms | **完全一致**（边界误差 ≤1–2ms，来自我 t0 估计） |

### 2.2 是否"像音游"：**否**

- **零节拍音轨**：整个 30s 内 WebAudio 振荡器只由"点中"产生（32×PERFECT + 10×GOOD = 84 个振荡器，与点击一一对应）；**开局 3 秒、以及全部 17 次漏拍，振荡器数 = 0**。生产包复测同样为 0（2.5s 不点 → count 0）。即：没有任何节拍/伴奏/漏拍音。
- **没有预备拍/倒计时**：点开始后 0.6s 直接第一拍。
- **唯一节拍线索 = 一个 16px 圆点闪 2 帧**：59 个静态圆点排成 5 行（行距 22px），到拍时该点 `class=beat on`：
  - 闪烁开始比拍点**早约 15ms**（中位 −16.0ms，即 60fps 相位锁定的取整结果），
  - 可见时长**中位 37ms、最长 52ms**；
  - 指示点每拍跳 22px，**换行时一次跳 264.9px**（4 次）。
- 因此"看闪点→反应着点"必然错过：人手视觉反应 ~200–250ms，落在 160–240ms 的**双罚带**（见下）。
- 模拟"能靠内部节拍预测、σ≈80ms 抖动"的玩家：40 拍 = 29 PERFECT / 9 GOOD / 2 MISS，得分 640（参考满分 1180 的 54%）。也就是说：只有**不依赖视觉反馈、纯靠内在 500ms 节拍**才能打高分。

判定文字/音效同步本身没问题：PERFECT 音 = 660→880Hz 双音（第二音 +90ms）；GOOD 音 = 406+609Hz 同时双击；MISS **完全静音**（只有红字 + 褐点）。

### 2.3 判定是否公平：**有两处不公**

1. **"差一点"比完全不点更亏（双罚 -15 vs -10）**：δ 在约 **160–220ms** 时，tap 先判 miss **−5**，随后该拍的"漏拍"又在 +220ms 判 **−10**，合计 **−15**；完全不点只 −10。
   实测：δ=+0.175 / +0.20 / +0.21 / +0.22（以及 −0.175 / −0.20 / −0.24）全部产生 **−15** 跳变。
2. **"晚按合并"只在错过后才生效，罚分非单调**：同一量级的早/晚偏差，δ=+0.235、−0.26 额外罚分 0（合并进了漏拍），但 +0.21 要罚 −15。规格写"晚按 240ms 内与漏拍合并、不双罚"，实现里 `nearMissed` 只检查"已 used 的拍"，160–220ms 这一档从未被合并 —— **规格与实现不符**。
3. **漏拍扣分不刷新分数显示**：节奏的 tick 分支里 `score -= 10` 后**没有** `scoreEl.textContent = ...`（咖啡 tick 每帧刷新，只有节奏漏了）。实测分数日志在漏拍时刻**没有任何记录**，−15 是在"下一次点击"时一次性跳变。玩家漏拍时看到的是"分数不动"。

### 2.4 结算

实测一局：560 分（perfect 32 · 漏拍 17）、奖励 **+15**（560/1180×30 保底档）。结算明细只报 perfect/漏拍，**不报"乱点/误按次数"**。

## 3. 接咖啡

| 项 | 实测 |
|---|---|
| 时间窗 | ±0.32s 确认：δ=+0.31 接住、+0.35 没接住；−0.31 接住、−0.35 没接住 |
| 横向窗 | dx=0.10 接住、dx=0.15 没接住（规格 ±0.13）；画出的咖啡 22px，区域宽 322.8px → 判定半宽 **42px vs 视觉半宽 11px ≈ 3.8 倍** |
| 纵向 | **完全不参与判定**：点在面板任意高度（我在 50% 高度点）都能接住杯口的咖啡 |
| 视觉 vs 判定 | 杯口线在 86.16%（258px），咖啡在 at 时刻顶部到 88%（264px，已在杯口线下方 5.5px）；落地变暗 `.landed` 在 at+0.005–0.015s 就出现，但 **到 at+0.32s 之前仍可接住**（实测 δ=+0.20、+0.31 接住，元素 class 同时是 `drop landed caught`）→ "看起来已经掉了/变暗了还能接" |
| 音效 | **整局 0 个振荡器**（26.5s 内），接住只有绿闪+1.4 倍缩放 180ms 和分数，漏接只是变暗消失 → 全程静音 |
| 分数刷新 | 每帧刷新（正常），接住 +10×连击加成（上限 ×2），漏接 −2 |

另发现一个真实性能问题：**每帧为"已结算的旧掉落"重新创建/移除 DOM**（tick 里 `els.delete` 后下一帧又因 `dt < -0.6` 重新 create+append+remove）。实测 26.5s 一局 **18,894 次 `.drop` 节点插入 ≈ 713 次/秒**；后段（~27 个旧掉落同时存在）≈ 27 次/帧的创建+回收。

## 4. 找老板

- 点击→重渲染 **0.8ms / 0ms**（同步），格子 94×64px（可点）。
- 找对 +50，找错 −20，重启一轮立即刷新。
- **整局 0 个振荡器**：找对/找错都无声；也没有"对/错"文字反馈（只有分数数字和"已找 N"）。
- 60ms 内连点两下 = **被算成两次作答**（第二下按刷新后的新局判，实测两下都 +50；乱点 12 下 130→100 → 会被连点误判）。
- 分数为 0 时点错，界面**完全没有变化**（−20 被 clamp 到 0）→ 与"死点击"无法区分。

## 问题清单

### P0
- 无。

### P1
1. **节奏：漏拍 −10 不刷新分数显示**（`arcade.ts` 节奏 tick 分支缺 `scoreEl.textContent`）。实测漏拍期间分数冻结、下次点击才跳变；结算分数低于玩家最后看到的分数。→ 假反馈，直接影响判定信任。
2. **节奏：160–220ms "差一点"双罚 −15 > 完全不点 −10，且罚分非单调（+0.235/−0.26 反而免罚）**；规格"晚按 240ms 内合并、不双罚"未实现（合并只认"已 used 的拍"）。→ 判定不公，越努力越亏。
3. **节奏：无节拍音轨/无预备拍/无接近提示**，"跟着节拍点"只能靠内在计时；唯一视觉线索是拍点瞬间闪约 2 帧且比拍点早约 15ms。→ 不像音游，且看闪点反应必然落进双罚带（与 P1-2 叠加）。
4. **接咖啡整局 0 音效；找老板整局 0 音效、对/错无文字提示**（3 个迷你游戏里 2 个全程静音）。→ 操作党最核心的"命中有反馈"缺失。

### P2
1. 节奏结算只显示 perfect/漏拍，不显示"乱点/误按"次数（玩家不知道自己被扣在哪儿）。
2. 节奏失配 −160~−240ms 早按也双罚；建议统一为"超出 GOOD 直接并入漏拍，不额外扣 5"。
3. 咖啡：`.landed`（变暗）在 at+0.01s 出现但可接窗口到 +0.32s，视觉与判定不一致（"掉下去还能接"）；横向判定 3.8 倍于咖啡图形、纵向完全不判 → 建议收缩或加判定反馈提示。
4. 咖啡：已结算掉落每帧重建 DOM（实测 18,894 次插入/26.5s，后段 ≈27 次/帧），纯浪费，低端机有掉帧风险（崩溃/卡顿类）。修法：`resolved` 后从 `drops` 里剔除或直接 `continue`。
5. 找老板：60ms 双触被算两次作答；分数为 0 时"找错"无任何可见变化；建议加 150ms 冷却 + "对/错"微反馈 + 错误音。
6. 老板回合制：150ms 防误触守卫被 `click` 兜底路径绕过（守卫只拦 pointerdown）；建议 click 路径同守卫。
7. 老板回合制：计时条以"面板出现"为 0 点，真实窗口以"事件开始"为 0 点 → 最后 16–141ms 显示还有时间但已判超时；建议条形用 `es.bossUntil - gameTime` 驱动。
8. 巡逻 type/blitz：达标后确认延迟 6.3–7.0s（等窗口结束）；建议达标即给"达标"音/飘字（奖励仍可窗口结束发）。
9. 点击 HUD 连击数字滞后 122–156ms（150ms 节流）；>12.5cps 连点 50% 静默丢弃（80ms 冷却）—— 建议超频时也给一次"太快"的轻反馈。
10. 2cps（间隔正好 0.5s）时连击完全不累积（窗口边界），与"连击 0.5s 窗口"的表述容易误解；可考虑窗口 0.55s 或文案写"约 2.5 次/秒"。
11. 无任何震动反馈（`navigator.vibrate` 0 处）；iOS 不支持，Android 可低成本补。
